# StackChan 桌宠形态：整体设计方案（会听、会看、不一定说话）

状态：设计稿（2026-11-15），未实现。
范围：M5Stack CoreS3 + StackChan 机身（`m5stack-stackchan` 板）。BOX-3 / CoreS3 只做共享改动回归。
与既有文档的关系：

- [stackchan-pet-behavior-plan.md](stackchan-pet-behavior-plan.md)（2026-09-21 草案、10-31 复核）偏「动作 / 触摸 / IMU / 音效」。本文吸收它的分层、触摸反应表、IMU 设计和缺陷 A 结论，不重复其细节。
- 本文新增四块：**屏幕视觉语言整体重做**、**观察（摄像头）**、**倾听（不说话也能被感知在听）**、**灯语**；并参照 Reachy Mini 的注视中间层，在设备上建一个本地注意力层。
- 所有改动都落在现有架构内，「不能破坏的机制」写成 §2 的不变量，作为评审和验收的硬约束。

## 0. 结论先行

1. **定位**：StackChan 是一只常驻桌面的小生物。大部分时间它在**陪伴态**：活着、四处看、对你和环境有反应、不说话。你点它的脸，它进入**倾听态**（现有 half duplex 会话，语音回复默认关）：专心听，用眼神、头和灯回应。没人理它就**犯困、睡着**。这不是新角色系统，同一个 Companion 的身份、人格和记忆不变，宠物式表现只是这台设备的输出方式。
2. **屏幕**：放弃现在「暖纸底色 + 绿色舞台卡片 + 顶栏文字 + 底部按钮」的终端式布局，改为**一个有身体的小生物**（§4.8–4.11）：深色底上的发光眼（釉光：外辉光、渐变、可选扫描线、曲线眼睑），屏幕上沿两角是耳朵或触角，眉毛和小嘴只在强情绪时浮现，再加粒子特效、思绪气泡、一瞥信息卡和极淡的昼夜 / 天气氛围层。**耳朵是新的主表达通道**：采音时头不能动，耳朵可以竖、转、抖。同一套表情状态可以用三种画风画（釉光 / 像素 / 萌宠），五系角色的差异是耳形和眼形，不只是换色。默认仍然无嘴，不会出现「有口型没声音」。
3. **表情不是枚举，是参数**：把现有 `FacePose` 扩成一组眼睛参数（大小、挤压、圆角、上下眼睑与角度、视线、高光、腮红、可选小嘴、装饰符号），心情 / 注意力 / 会话阶段 / 瞬时手势 / 眨眼按固定顺序合成。另有 8 个特殊眼型（心、星、漩涡、笑弧、满足弧、挤眼、闭眼线、×），用「先压成横线再展开」的过渡切换。Host 侧 `face-core-1` 的 8 个手势 ID **一个都不改**，只在设备内部换皮。
4. **感知全景**（§6.1）：机身上所有能感知外界的器件都纳入：屏幕触摸、头顶三区触摸、IMU（含片上敲击 / 静止检测）、磁力计、接近 / 环境光、摄像头、双麦、两个舵机的位置 / 负载 / 电流 / 温度读回、电源与底座电流、RTC、红外接收、NFC。**舵机本身就是传感器**：指令没变而位置变了，说明有人在掰它的头。再加 Host 提供的外界信息：时间、主人在不在家、家居状态、天气、提醒。多路信号融合成少量可解释的判断（被拿起、躲猫猫、关灯睡觉、敲桌子叫它……），每个判断对应一组反应。
5. **观察**：设备本地的注意力层，结构照搬 Reachy 的 `sources → policy → actuators`：触摸、接近、IMU、摄像头运动 / 人脸都只产生「候选目标」，一处仲裁，执行时**先眼后头**。随机扫视明确标为「不是目标」，不冒充「在看你」。只判断「有人 / 在哪」，不识别「是谁」，帧不出设备。
6. **摄像头要先过闸门**：它被关掉的原因写的是「饿死 full_duplex AFE」，而 StackChan 现在是 half duplex + raw 采集，没有 AFE。这条理由可能已过时，但必须先实测内部 SRAM 低水位再开。过不了闸门就采用「陪伴时看、倾听时关相机」的降级方案。
7. **倾听**：会话里麦克风开着时，现在会切断舵机电轨。复核（§6.6）证明噪声问题属实（舵机供电时底噪高约 20 dB），但「必须断电」不是唯一解，需要在设备上分工况实测。在实测之前，「在听」交给耳朵、眼睛和灯：耳朵竖起并随你的音量轻抖，眼睛看着你，灯带显示音量条。待机「环境耳」（本地听声响、不上行）列为可选的后期项，默认关。
8. **灯语**：12 颗灯（左右各 6）只承载少量语义：采音中、思考中、注意方向、被抚摸、充电中、离线。默认克制、低亮度，夜间全灭。
9. **顺序**：先修缺陷 A、定待机输出权限 → P0 新脸（釉光 + 耳朵 + 眼型字形 + 眼神活性，纯设备侧）→ P1 机身传感器（头顶触摸、接近光、IMU、舵机读回、电源、RTC）与头部仲裁 → P1.5 摄像头实测闸门 → P2 会看 + 外界信息（`body.ambient.set`）+ 角色皮肤 → P3 环境耳、NFC 卡、磁铁玩具、红外、表演类动作。

## 1. 产品定义

### 1.1 三种生活状态 + 系统态

| 状态 | 什么时候 | 它在做什么 | 麦克风 | 头 | 主要表达通道 |
|---|---|---|---|---|---|
| 陪伴（Ambient） | 待机，设备绝大部分时间 | 呼吸、眨眼、四处看；有人靠近、被摸、被拿起时有反应；注意到动静会看过去 | 关（StackChan 已关唤醒词） | 可动（缺陷 A 修好后） | 眼 + 头 + 灯 |
| 倾听（Listening） | 点脸进入现有会话 | 看向你、专心听；你说完它想一想，再用表情和动作回应；字幕可选 | half duplex 开 | 采音时不动；回应窗口内可动 | 眼 + 灯；回应时加头 |
| 休息（Rest） | 精力耗尽、夜间、环境暗 | 眼皮渐垂 → 睡着（闭眼、慢呼吸、灯灭）；被摸 / 被叫醒时不情愿地醒来 | 关 | 低头静止 | 眼（极暗） |
| 系统（System） | 配网、联网、更新、恢复、出错 | 清楚说明发生了什么、要做什么 | 按现有逻辑 | 静止 | 文字页 + 小号表情 |

### 1.2 体验原则

1. **克制比热闹重要**。大部分时间是低活动基态，偶尔有小动作；不要一直兴奋、一直转头。舵机有声音、耗电、有寿命，日常「活着」主要靠眼睛。
2. **只有真目标才「看你」**。随机扫视是生物感，不是注意力；没有目标来源时不能表现得像认出了人。
3. **反应先于理解，理解来自 Eidolon**。本地反射（被摸、被拿起、有动静）立即出现；「确认、关切、已记住」只能来自 Agent 的语义结果，不能用随机开心冒充理解。
4. **会话状态必须可辨认**。采音开关独立可见（屏幕图标 + 灯），情绪动画不能充当唯一的麦克风提示。
5. **长时间盯着人会让人不舒服**。互相注视时要有慢眨眼和偶尔移开视线。
6. **它看见了什么只留在设备上**。注意力层只知道「有人 / 方向 / 远近」，不知道「是谁」。

与 Reachy 注视中间层的对应关系（[attention-architecture.md](../../eidolon_client_reachy_mini/docs/attention-architecture.md)）：

| Reachy | StackChan | 说明 |
|---|---|---|
| `GazeCandidate`（source/kind/bearing/confidence/ttl） | 同构的 `PetCandidate` | 多一个 `is_target`：空闲生成器的点为 false |
| `AttentionPolicy.decide`，优先级写死在一处 | `PetAttentionPolicy`，同样一处、可单测 | 规则见 §6.2 |
| `FaceDelegation` 的 search→track→hold→recenter | 同样四阶段 | 参数按 2–5 Hz 检测和弹簧舵机重定 |
| 先头后身（`BodyGate`） | **先眼后头** | 眼是零成本执行器，头是昂贵执行器 |
| 自身播放时忽略 DoA；Host `user_speaking` 门控声源 | 头在动时忽略相机帧差；采音电平只在会话里用 | 同一个「自噪声」原则 |
| `attention.state` 事件（会话内） | 会话内可复用同一事件 | P2，契约已在 SDK |
| 不上传帧、不做身份 | 同 | I10 |

代码落点（建议）：

- `main/eidolon/pet/`：`pet_mind`、`pet_attention`、`pet_liveness`、`pet_clip`、`pet_composer`，与板无关、不依赖 LVGL / FreeRTOS，host 测试覆盖。
- `main/eidolon/views/pet_face_skin.*`：自绘眼睛渲染器，挂在 `CompanionFaceView` 内，替换 StackChan 上的 `DefaultAvatar`。
- `main/boards/m5stack-stackchan/`：传感器驱动（Si12T、LTR-553、BMI270、相机采样）与执行器适配（头、灯）。
- 时钟：脸跟 LVGL 20 ms timer；头跟现有 50 Hz `UpdateLoop`；Si12T / LTR-553 挂同一 tick 分频轮询；相机采样是唯一需要独立 worker 的部分，且只在相机闸门通过后存在。

## 4. 屏幕：视觉语言重做

### 4.1 三个方向与推荐

| 方向 | 样子 | 优点 | 问题 | 结论 |
|---|---|---|---|---|
| A 经典 Stack-chan | 黑底、白色圆眼、一字嘴（社区 m5stack-avatar 风格） | 辨识度最高，社区认知强 | 嘴在不说话时制造「怎么有嘴没声音」的预期；表现力主要在眼睑；Stack-chan 角色可商用但须按其 GUIDELINE 署名作者，不宜作为自有品牌形象 | 可选「复古皮肤」，做则署名 |
| **B 发光程序化眼** | 深色底、两只圆角矩形发光眼，默认无嘴；靠形状、眼睑、视线、挤压表达（Vector / Emo / RoboEyes 一系） | 最适合不说话的宠物；参数连续，注视、扫视、眨眼自然；绘制便宜 | 情绪辨识依赖配方打磨，要做辨识测试 | **默认皮肤** |
| C 卡通整脸 | 眼、眉、嘴、腮红俱全（Kawaii Face 一类） | 情绪辨识最强 | 更像「屏幕里贴了张脸」，和实体头部结合时不如 B 像「这个生物的眼睛」；canvas 方案约 97 KiB | 只借它的腮红 / 符号做点缀层 |

推荐 B 作为默认画风，并补上「身体」（§4.8）。样机提供三种画风切换：

- **釉光**：B 的完整版，外辉光、渐变、扫描线、曲线眼睑。
- **像素**：Dasai Mochi 式粗像素。同一套参数画在 1/4 分辨率网格上，绘制最便宜，复古可爱。
- **萌宠**：浅色脸底 + 深色大眼珠 + 双高光，最可爱，适合有小孩的家庭（C 的气质，但仍是同一套参数）。

三者都消费同一个 FaceState，只是绘制器不同（Stack-chan 官方「FaceState 驱动可替换皮肤」的做法）。最终选一个做默认，其余作为皮肤。五系角色（§4.7）是形体变体，不是五套渲染器。

### 4.3 参数化眼睛（FacePose v2，设备内部）

现有 `FacePose` 只有视线、开度、倾斜、大小、嘴开度。扩为：

| 参数 | 范围 | 视觉含义 | 现有字段映射 |
|---|---|---|---|
| `gaze_x / gaze_y` | −1…1 | 眼睛整体平移（±30 / ±20 px），高光随之偏移 | 同名 |
| `open_l / open_r` | 0…1 | 眼高缩放（眨眼、困倦、眯眼） | `left_open / right_open` |
| `scale` | −1…1 | 整体大小（惊讶放大、害怕缩小） | `eye_size` |

### 4.5 合成顺序（单线程，一次合成）

```
最终姿态 = 心情基态
         ⊕ 会话阶段基态（Listening / Thinking / Error，有则覆盖相应字段）
         ⊕ 注视（gaze 字段，来自注意力层；无目标时来自空闲生成器）
         ⊕ 瞬时层：Host 手势（会话槽） 或 本地反射 clip（本地槽），二者互斥，Host 优先
         ⊕ 微活性：呼吸缩放、微扫视
         ⊗ 眨眼：只临时乘到开度上，结束后恢复当时的基态
         + 装饰：最多 2 个，固定容量
```

关键规则：

- **按参数类型合成**（借 Vector 的层叠规则）：位置、角度类（gaze、lid_angle）相加；缩放类（scale、squash）相乘；眼睑覆盖类（lid_top、lid_bottom）取最大；高光、腮红取加权平均。这样预制配方和程序化层（眨眼、扫视、注视）叠在一起不会互相冲掉，也不会越叠越偏。
- 现有 `Runtime` 只有一个 Plan 槽。新增**本地槽**给反射 clip：Host 计划到达时，本地 clip 静默取消、不产生回执；Host 计划在跑时本地 clip 直接不播。Host 计划的 `Accepted / Started / Completed` 时机与现在完全一致（I2）。
- 现有「手势期间眼睛强制睁开、自动眨眼不能覆盖」的规则保留并推广到本地 clip。
- 空闲眼神全部在设备本地运行，不需要会话授权（与现在的自动眨眼同类）。

### 4.6 渲染实现与预算

- 每只眼一个 LVGL 对象，`LV_EVENT_DRAW_MAIN` 自绘：先画圆角矩形，再用底色三角形 / 矩形「切」出上下眼睑和斜度，再画高光点。**不用对象旋转**（LVGL 9 的 transform 会生成中间图层），斜眼用不对称眼睑实现。不分配全屏 canvas。
- 只失效两只眼的包围盒（约 2 × 110 × 130 px，约 57 KB / 帧）。SPI 40 MHz 下约 11 ms，动画期 30 fps 有余量；静止时只在眨眼 / 扫视时刷新。全屏底色只在切换场景时刷一次。
- **呼吸**：默认连续缩放、15 fps 刷新（§4.13，为了灵动）；省电模式退回阶梯式（8 级、每 600 ms 一步，M5 官方固件的做法）。
- **眨眼快闭慢开、带挤压**：总长约 150 ms（困倦时 300 ms 以上），闭合段约 40%，闭到底时眼睛压成一条略加宽的横线（Vector 的眨眼关键帧做法），间隔 2.5–6 s 随机，15% 概率连眨两次。
- 表情切换用 150–300 ms 的 ease-in-out；视线扫视 50–80 ms，比其它参数更快。

**釉光画风在本机 LVGL 配置下的做法**（已核对 `sdkconfig`：`LV_USE_DRAW_SW_COMPLEX_GRADIENTS` 未开、`LV_USE_VECTOR_GRAPHIC` 未开、`LV_USE_CANVAS=y`、简单图层缓冲 24 KB）：

| 效果 | 做法 | 代价 |
|---|---|---|
| 外辉光 | 预烘焙 A8 柔光椭圆，3 档尺寸，按眼色着色绘制（A8 着色是单色混合，很便宜）。不用实时模糊或阴影 | 每档约 120×140 B ≈ 16 KB，放 PSRAM |
| 眼体渐变 | LVGL 原生竖向线性渐变（不需要 complex gradients） | 低 |
| 扫描线 | 每 3 px 一条 10% 暗线，裁剪到眼内 | 低，可关 |
| 曲线眼睑 | 用底色大圆 / 椭圆覆盖代替直线三角 | 低 |
| 高光视差 | 主、次高光随视线反向微移，显得眼睛是球面 | 低 |
| 耳朵 / 触角 | 每只一个自绘对象，三角 / 椭圆 / 圆组合，旋转用顶点计算而不是对象 transform | 低 |
| 粒子 | 固定 12 个对象池，16–24 px A8 小图 | 低 |

最复杂帧（双眼光晕 + 渐变 + 扫描线 + 耳朵 + 4 个粒子）必须实测。超预算时按「扫描线 → 光晕 → 渐变」的顺序逐级关闭；像素画风是最便宜的兜底。
- 装饰沿用现有 40×40 RGB565A8 资产（约 22 KiB），并发上限 2，对象复用，不用无上限的对象池。
- 真实帧回执沿用 `prepared_frame / completed_frame` 机制，Host 计划仍然只在真实刷新完成后报 started / completed。
- 预算（待测）：动画帧绘制 ≤ 8 ms、LVGL task 占用 ≤ 25%、内部 SRAM 低水位不低于现基线 2 KB 以上、PSRAM 增量 ≤ 64 KB。

### 4.9 动效原则

- **每个参数一个弹簧**：视线略欠阻尼（ζ≈0.65，停下时过冲一点，显得有重量）；大小、挤压、眼睑临界阻尼。
- **预备动作**：大幅扫视前，眼睛先向反方向缩一下（约 40 ms）。
- **跟随与惯性**：头转动时眼睛先滞后、再追上；头停下时眼睛轻轻晃一下（follow-through）；耳朵比头晚约 80 ms 到位。
- **眼型过渡**：换眼型时先压成横线（约 80 ms），换形后再展开（约 120 ms），掩盖形状突变。
- **安静是常态**：大部分时间只有眨眼、微扫视和阶梯呼吸；明显的动作留给真实刺激。

### 4.10 特效、思绪气泡、一瞥信息卡、氛围层

- **粒子**：心（被摸、零食）、星（惊喜）、泪（委屈）、汗（尴尬、被挡住）、Zz（困）、音符（音乐）、火花（开心爆发）、尘（放回桌面）。固定池 12 个，带速度、重力和寿命，用完复用。
- **情绪符号**：右上角一次只放一个：「!」「?」「#」「…」。
- **思绪气泡**：外界信息的「无字表达」（§6.1 B）。下雨 ☔、该睡了 🌙、提醒 🔔、有人回家 🏠、在放音乐 ♪、饿了（低电量）🔋、在吃饭（充电）⚡。宠物先瞟一眼气泡，再看回你；点气泡展开信息卡。
- **一瞥信息卡**：陪伴态双击头顶（或在屏幕上向上滑）时，底部滑出一张卡：大号时间、天气、下一个提醒，宠物低头看着卡，4 s 后收回。这让它同时是一个有用的桌面摆件（Emo、Dasai Mochi 都有时钟），但不抢主角。点卡片之外的地方仍然是开始对话。
- **氛围层**（可关，永远不压在眼睛上）：夜里背景几颗缓慢闪烁的星点（只改透明度）；下雨时边缘有细雨丝（10 fps）；下雪时飘几片雪；清晨上缘一条暖色带，傍晚一条淡紫色带。

### 4.11 三种画风的取舍

| | 釉光 | 像素 | 萌宠 |
|---|---|---|---|
| 气质 | 精致、科技感、夜里好看 | 复古、可爱、有「电子宠物」怀旧感 | 最可爱、最亲和 |
| 绘制代价 | 中（光晕、渐变） | 最低 | 中低（无光晕，大面积浅色底） |
| 夜间 | 好（深色底） | 好 | 浅色底偏亮，夜间需要整体压暗 |
| 和实体头部的结合 | 最像「这个生物的眼睛」 | 像屏幕里的宠物 | 像一张脸贴在头上 |
| 建议 | 默认 | 低电量 / 性能兜底，也可作皮肤 | 作为可选皮肤，面向家庭 |

### 4.12 画风、配色、角色是三个独立维度

| 维度 | 决定什么 | 选项 |
|---|---|---|
| 画风 | **怎么画**：眼睛的质感和整张脸的画法 | 釉光（深色底、发光眼，有光晕和渐变）；像素（同样的脸画成粗点阵，像老式电子宠物）；萌宠（浅色脸底、深色大眼珠加白色高光，像卡通动物） |
| 配色 | **用什么颜色** | 见下表 |
| 角色 | **长什么样**：耳朵、眼形、鼻头 | 小精灵、猫头鹰、小鹿、水獭、狐狸、小熊 |

### 4.13 灵动：一直在活，但活在眼睛和耳朵上

目标是让它看起来一直有心思，又不靠舵机（舵机有声音、耗电，采音时可能还不能动，§6.6）。

**物理感**

| 做法 | 参数（初值） | 效果 |
|---|---|---|
| 视线用欠阻尼弹簧，双眼刚度略不同 | ζ≈0.55；右眼比左眼慢约 15 ms | 到位时轻微过冲再停，两只眼不完全同步，不像机器 |
| 运动挤压拉伸 | 扫视越快，眼睛沿运动方向拉长，最多 25%，到位回弹 | 眼睛像有弹性的果冻 |
| 预备动作 | 大幅扫视前反向缩 6%、约 40 ms | 动作有「起势」 |
| 耳朵是更软的弹簧 | ζ≈0.4；眼睛一跳、头一停，耳朵跟着甩一下 | 次级动作，最便宜的生命感 |
| 情绪切换弹出 | 新表情先放大约 8% 再落回 | 变化有「啪」的一下 |
| 呼吸 | 连续缩放 ±2.5%，设备上 15 fps 即可 | 静止时也在活 |

**微行为库**（清醒、没有真目标、没有会话时，由调度器按心情加权随机挑选）：

|---|---|---|---|---|---|---|
| 张望 | 看向随机一点 1–2 s（标记为非目标） | 高 | 中 | 中 | 中 | 低 |
| 连眨 | 快速眨两下 | 中 | 中 | 中 | 低 | — |
| 单耳抖 | 一只耳朵抖一下 | 中 | 中 | 中 | 中 | 低 |
| 歪头 | 双眼反向倾斜、一眼稍大 1.3 s | 中 | 低 | 中 | 低 | — |
| 偷笑 | 眼睛弯一下 | 低 | 中 | 高 | — | — |
| 发呆 | 看向上方 1 s | 低 | 中 | 低 | 高 | 中 |
| 蹦一下 | 先压扁、再弹起、耳朵上甩 | 低 | 低 | 高 | — | — |
| 摇耳朵 | 两耳交替摆 | 低 | 中 | 高 | — | — |
| 哼歌 | 冒两个音符，眼睛弯 | — | 中 | 中 | — | — |
| 扫视房间 | 视线慢慢扫一圈 | 中 | 低 | 低 | 中 | — |

- 间隔：开心 1.8–4 s、平静 2.5–5.5 s、满足 3–6 s、无聊 4–8 s、困倦 5–9 s。
- **有人在旁边时更活跃**（接近 / 人脸 / 5 分钟内有互动）：空闲时间约 25%，微行为密集；没人时回到 60% 以上空闲（Reachy 的做法），省电也不扰人。
- 微行为几乎都只动眼睛和耳朵；「歪头」「张望」只在电轨可用、精力高的时候顺带一点头部动作。
- **互动即时性**：手指一按，眼睛 50 ms 内看过去；在头顶来回摸时，眼睛跟着手的位置、耳朵顺着摸的方向倒；松手后有余韵（满足地眯一会儿再恢复）。
- 设备代价：微行为只刷新眼睛和耳朵的包围盒，活跃期 30 fps，估计平均约 40% 的时间在动，功耗和帧时间需实测。

注意两点：

- **前后方向的定义**：BSP 把通道倒序，出厂固件不倒序，两边的「前滑」方向相反。我们统一定义为「从脸往后脑 = 顺毛」，在驱动层固定一次，不在上层再取反。
- **舵机运动会干扰电容触摸**：第三方实测在舵机摇头后，三区读数可能卡在满值将近 2 分钟，调用 recalibrate 能恢复。所以舵机运动期间和停止后 500 ms 内忽略触摸；三区同时满值超过 3 s 就自动重新校准。这也和 §6.6 的舵机电源噪声属于同一类问题，实测时一并记录。

此前的宠物方案 §3.3 按「左 / 中 / 右」写触摸区，硬件实际是前 / 中 / 后，以本节为准。

可直接参考的驱动：Si12T / LTR-553 / GC0308 / PY32 灯见 ciniml/stackchan-idf（BSL-1.0）与出厂固件（MIT）；BMI270 / BMM150 用 Bosch 官方 API；红外用 ESP-IDF RMT 例程；INA226、BM8563 寄存器简单。移植前逐个核对许可。

设备只把它们映射成心情、气泡和氛围，不回传任何感知结果。Owner 可在 Mobile 按类别关闭。

| 被掰头 | 不在执行指令时位置偏离 > 6° 且负载反向；或执行指令时实测落后 > 10° 持续 300 ms | 挤眼「> <」抵抗一下再顺着，松手后回位 | 现有堵转保护优先；持续卡住判为「被挡住」 |
| 被挡住 | 指令未达、电流高、位置 600 ms 不变 | 委屈：眼睑下垂 + 汗；轻试一次后放弃 | 同上 |
| 有人靠近 | 接近值上升 / 相机运动 / 人脸出现，任一 | 先抬眼（预期），再注意 | 习惯化（§6.2） |
| 躲猫猫 | 接近 = 很近 + 画面骤暗 + 屏幕无触摸，持续 > 500 ms | 「看不见了」：眼睛四处找、「?」；移开 → 星星眼 + 开心 | 夜间关灯是缓降、接近不触发 |
| 关灯了 | 环境光 1 s 内下降 > 70% 且接近不触发；夜间加权；Host「灯全关」可直接确认 | 打哈欠 → 困倦 → 睡着 | 背光变化后 1 s 内的光感样本丢弃 |
| 早上了 | RTC / Host 时间进入起床时段 + 环境光上升 | 伸懒腰、慢慢睁眼 | — |
| 充电 / 被带走 | VBUS 插入 / 拔出 | 「吃饭」/ 竖耳张望 | — |
| 主人回来 | Host `body.presence.set awake`；本地辅证：门开事实 + 人脸出现 | 迎接 | 以 Host 事实为准，本地不冒充识别 |
| 有人用遥控器 | 收到 38 kHz 遥控码 | 看向电视方向，陪看 | 只判有无码，不解码用途 |
| 音乐 | 环境耳：持续能量 + 周期性节拍；或 Host「正在播放」 | 音符、跟拍摇头、灯随拍 | 会话中不触发 |

**D. 采样调度与总线预算**

所有 I2C 器件共用一条总线（与音频编解码器配置、屏幕触摸、PY32 灯和舵机电轨共享），所以采样频率按需分配：

| 器件 | 频率 | 说明 |
|---|---|---|
| FT6336U | 现有 LVGL indev | 不变 |
| Si12T | 20 Hz | 只读 3 通道强度 |
| BMI270 | 片上 FIFO 每 200 ms 批量读；tap / any-motion / no-motion 用片上检测 | 中断脚若未接到 MCU，就 20 Hz 读状态寄存器 |
| BMM150 | 2 Hz，仅玩法开启时 | |
| LTR-553 | 接近 10 Hz、照度 2 Hz | |
| AXP2101 | 1 Hz + 电源键事件 | 现有 |
| INA226 | 5 Hz | |
| BM8563 | 启动时 + 每小时校准 | |
| ST25R3916 | 低功耗卡检测唤醒，发现卡才读 | 默认关 |
| PY32 | 写 ≤ 20 Hz | 现有 |

- 舵机读回走独立的 UART 总线，挂在现有 50 Hz `UpdateLoop`：每 tick 轮流读一个舵机的位置，负载 / 电流 5 Hz，温度 / 电压 0.2 Hz。红外走 RMT，摄像头走 DVP，都不占 I2C。
- 用一个合并的 `pet_sense` 采样任务（约 3 KB 栈）按分频轮询全部 I2C 器件，而不是一个器件一个任务；结果写入固定容量的环形缓冲，由 Pet Runtime 在 LVGL tick 里消费，不进控制器事件队列（I9）。
- I2C 实际占用率要实测，目标 < 15%；超了先降接近和 IMU 频率。
- 功耗：背光和舵机最大，其次摄像头。电池供电时自动关摄像头和环境耳，接近降到 2 Hz。

触摸反应的具体表（tap、抚摸、连拍、滑动、被摸醒）和 IMU 反应（眩晕、被举起、倾斜补偿）沿用 [宠物方案 §3.3–3.4](stackchan-pet-behavior-plan.md)，本文只把它们接到统一的仲裁和合成上。

### 6.2 仲裁规则（一处、可测）

优先级从高到低：

1. `safety.stop` / 撤权 / 会话结束清理：一切本地动作挂起，直到下一个显式动作或会话结束（宠物方案 §4.2 规则）。
2. 服务端头部命令（`head.gesture` / `look_at` / `home`）和 Host 表情计划：抢占所有本地层；本地层取消不上报。
3. 本地反射（触摸 / IMU）。
4. Host 对话对象锁定（P3）。
5. 人脸目标 > 运动目标 > 接近 > 触点。
6. 空闲生成器（只能产生扫视和张望，不能进入「盯住 / 互视」）。

锁定与释放要有迟滞（参数取自 stackchan-kai，真机再调）：运动目标连续 3 次检测命中才锁定，1.5 s 无运动释放；人脸命中 3 次锁定，连续漏检 10 次释放；目标方位用 EMA 平滑（系数约 0.2）。

防躁动规则（Reachy 真机教训：未门控的声源让头每 2.5 s 乱转一次）：

- **习惯化**：同一方位反复出现运动但始终没有人脸（窗帘、风扇、电视），该方位的响应强度按次数衰减，几分钟后恢复。
- **冷却**：头部转向之间至少 1.5 s；反向转回 2 s 内不再触发。
- **自运动抑制**：头在动或停下后 300 ms 内的相机帧不做帧差；屏幕背光大幅变化后一帧也丢弃。
- **精力调制**：精力低时只动眼不动头；睡着时只有触摸、被拿起和强运动能唤醒。

### 6.3 执行：先眼后头

1. 眼睛在 50–80 ms 内扫到目标方位（零成本、永远可用）。
2. **小偏差只动眼**：偏差 ≤ 20° 由眼睛承担；> 20° 且持续 ≥ 300 ms、头可用时，头用弹簧缓动跟过去（限速 ≤ 60°/s）。Stack-chan 官方取 30°，20° 是初值，真机再调。目标稳定停在一侧 > 2 s 且偏差 > 10° 时，头再慢慢补齐，让眼睛回到中央附近。
3. 头转动期间眼睛反向补偿，保持「盯着」目标；头到位后约 50 ms 释放力矩（Stack-chan 官方做法），既降噪又省电。
4. 盯着目标时保留极小的微扫视（每 0.5–1.5 s、约 2 px、66 ms 后回位），否则看起来像死盯。
5. 目标丢失：原位停 0.5–2 s → 沿离开方向多看一点（约 1.3 倍）找 300 ms → 1 s 慢回正（search → track → hold → recenter）。
6. 头不可用（采音中、电轨断开、安静时段、低电量）时，只做第 1 步，并把眼睛平移范围放大到 ±40 px 弥补。

方位换算：相机像素 → 以**拍摄时刻**的头部角度为基准换算到机身坐标（Reachy `PoseHistory` 的简化版：用 50 Hz 循环记录最近 1 s 的指令角度），避免「用当前头姿叠加旧画面」导致过冲。StackChan 舵机有位置读回，P2 可改用读回角度。

### 6.4 摄像头可行性闸门（P1.5，必须先做）

事实：

- 当前 `EIDOLON_STACKCHAN_ENABLE_CAMERA 0`，注释写的原因是「DVP 相机的内部 / DMA SRAM 饿死 full_duplex AFE 采音任务（8 KB 内部栈）」。
- StackChan 现在是 `half_duplex`、`USE_DEVICE_AEC=n`、`capture=raw`，**不走 AFE**。原因可能已过时，但内部 SRAM 仍然很紧，不能凭推理就打开。

闸门测试（真机，日志取证）：

| 步骤 | 条件 | 记录 |
|---|---|---|
| 1 | 开相机，QVGA YUV422 / 灰度，2 fps 采样，待机 30 min | 内部 SRAM 空闲、最大连续块、低水位；PSRAM；帧耗时 |
| 2 | 在 1 的基础上连续开关会话 20 次（half duplex） | 会话是否都能建立；低水位；音频丢帧；是否复位 |
| 3 | 会话中保持相机采样 | 同上 + STT 质量对照 |
| 4 | 会话中暂停相机（停流、释放 DMA 缓冲），结束后恢复 | 恢复耗时、是否泄漏 |

决策：

- 步骤 2、3 都通过：相机全时可用。
- 只有 2、4 通过：**陪伴时看，倾听时关相机**。产品上说得通：你和它说话时它专心听，用最后一次看到的方位保持注视。
- 2 不通过：相机暂不启用，观察只靠触摸 / 接近 / IMU，等内存优化（缓冲迁 PSRAM 等）后再测。

算法分两级，都在设备上：

1. **运动网格**（P2 先做）：复用 [guard_motion.h](../main/eidolon/guard/guard_motion.h) 的 24×18 亮度网格与运动分。这是纯函数，从 Guard 目录抽到共享 `vision/` 目录，不链接 Guard 服务（I10）。帧差得到运动质心与强度，几乎不占内存。
2. **人脸检测**（P2 后段）：esp-dl 人脸检测模型，2–5 Hz，只输出框的位置和大小（大小 → 远近）。不做特征提取、不做识别。先在 StackChan 上测单帧耗时和内存，预算 ≤ 150 ms / 帧。

### 6.5 倾听：不说话也让人知道它在听

会话中（P0 即可做，无新隐私面）：

- 进入会话时（OpeningConversation，约 0.7–1.1 s，此时麦克风尚未打开、头可动），头转向最后一次看到人的方位并抬起（perk），眼睛 attend。
- 采音开始：电轨按现有门控切断，头停在原位。**耳朵接过头的工作**：双耳竖起，随 `eidolon_livekit_board_recent_capture_rms_ppm()` 轻轻抖动（小精灵皮肤是触角尖随音量变亮）；眼睛进入倾听配方看着你，灯带显示音量条。你说话时它「随着声音微微动起来」，但没有任何机械运动。
- 你说完（Host 推送 Thinking）：思考配方 + 灯带流动。
- 回应：Host 的表情计划 + 头部手势（动作窗口内麦克风关、电轨开，现有逻辑）+ 可选字幕。语音默认关。

**采音时要不要断舵机电**：见 §6.6 的复核。在实测结论出来之前，按现状（断电）设计倾听表现；如果实测证明可以保持供电，倾听时就能加上前倾姿态和附和式的小点头。

待机「环境耳」（P3，可选，默认关）：待机时麦克风只算本地电平，**不上行、不做识别**；大声响 → 受惊抬头（电平上升沿超过阈值才触发，施密特迟滞防反复，本机播放期间屏蔽），持续音乐 → 跟着轻摆。它会在家里多开一个常开的麦克风，必须单独征得 Owner 同意并常亮指示，所以不作为默认能力。CoreS3 当前只用单通道采集，双麦间距小，**不承诺声源方向**。

### 6.6 采音时一定要给舵机断电吗？（2026-11-15 复核）

**结论**：问题是真的，而且很大；但「必须断电」没有被证明是唯一解。门控加进来时只证明了「舵机这条供电路径一开，麦克风底噪高约 20 dB」，没有区分是哪一部分在吵，门控本身也没在 StackChan 上验证过。需要一组分工况实测再决定。

| | 舵机开（5 次） | 舵机关（1 次） |

| 底噪 RMS（> 80 Hz） | −31.7 ~ −32.3 dBFS | −58.3 dBFS |

**分工况实测方案**（设备在线：USB 序列号 `68:EE:8F:D8:4A:04` 即这台 StackChan。复用 AEC 资格测试的原始录音与串口导出流程，app-only 刷入诊断构建，测完刷回生产版，不擦 NVS）：

| 工况 | 电轨 | 力矩 | 总线轮询 | 运动 |
|---|---|---|---|---|
| A | 断 | — | 无 | 无（基线，即现状） |
| B | 开 | 卸 | 无 | 无 |
| C | 开 | 持（home） | 无 | 无 |
| D | 开 | 持 | 50 Hz（现状空闲） | 无 |
| E | 开 | 持（前倾听姿） | 无 | 无 |
| F | 开 | 持 | 50 Hz | 呼吸式微动 ±2° |
| G | 开 | 持 | 50 Hz | 点头手势 |

每个工况录 10 s 静音 + 10 s 由 Mac 在 50 cm 外放的固定中文语音，算底噪、语音 SNR、主线频率；再读回断电前后的 pitch 位置，量化低垂幅度。

**实测结果（2026-11-15，在线设备，两轮共 14 段）**：诊断构建在 worktree 分支 `diag/servo-noise-qualification`（`main/servo_noise_qualification.cc` + `scripts/servo_noise_qualification/`），数据在 `reports/servo_noise/run-20261115-172041/` 与 `run-20261115-172505-reordered/`，测前按字节备份 ota_0，测后恢复并核对构建指纹一致。

| 工况 | 第 1 轮（固定顺序） | 第 2 轮（打乱 + 重复） |
|---|---|---|
| A 断电（现状） | −40.0（1831 Hz 纯音） | −63.4、−58.3 |
| B 通电、卸力、不轮询 | −40.4（1831 Hz） | −57.7 |
| C 通电、持力、不轮询 | −61.0 | −48.0（2048 Hz） |
| D 通电、生产空闲 | −62.3 | −60.4、−53.3 |
| E 通电、持力、50 Hz 轮询 | −61.3 | −56.7 |
| F 持力 + ±2° 呼吸微动 | −57.6 | — |
| G 连续点头 | **−24.6** | — |

（单位 dBFS，> 80 Hz，24 kHz 原始采集，每段 6 s。）

结论：

1. **底噪与舵机供电状态没有稳定对应。** 断电三次落在 −63 到 −40，通电各状态落在 −62 到 −48，两个分布完全重叠。噪声是一个时有时无、在 1.8–2.8 kHz 漂移的音，带 2 ms 成簇结构，断电时照样出现，来源更可能是别的开关电源（例如电源管理 / 充电芯片的轻载突发模式），不是舵机电轨。7 月「关舵机就安静」只比了各 1 s 的一段，被这种间歇性混淆了。
2. **舵机转动本身很吵**：连续点头时 −24.6 dBFS，所以用户说话时不做大动作；±2° 的慢速微动在安静范围内。
3. **断电后头几乎不下沉**（4 s 下沉 0.6°），但恢复供电后舵机要约 **750 ms** 才响应——这正是现在回应动作慢一拍的原因。
4. 按下面的决策规则：**采音时改为保持供电、持力不动**，只禁止动作，不切电轨；保留编译开关可回退到断电。间歇噪声的真正来源另行排查（电池 / USB 供电、背光、充电开关对照）。

**决策**：

- B 或 C 与 A 相差 ≤ 3 dB → 采音时**保持供电**（卸力或持力不轮询），头不再低垂，倾听时可以保持前倾姿态；附和式小点头看 F / G 的结果。**（实测满足此条，已采用。）**
- 只有 A 干净 → 保留断电门控，但改体验：采音前先把头放到断电后不下沉的姿态；把断电限定在「用户正在说话」那段（Host `user_speaking`），而不是整个倾听期。这需要另测服务端 VAD 会不会被 B / C 的噪声误触发。
- 同时向 M5 确认硬件解法：舵机电源轨加 LC 滤波、麦克风偏置去耦。

## 7. 心情与精力

沿用宠物方案 §4.4 的三标量（valence 愉悦、arousal 兴奋、energy 精力），按时间常数衰减回基线。本文补三点：

0. **用显式状态机，不做涌现式情绪**：Vector 官方文档记录过，涌现式情绪系统后来被降级，改为带冷却的显式状态转移，原因是更可控。这里也一样：生命基态之间是显式转移 + 最短停留时间 + 冷却，三个标量只用来判断转移条件和调制幅度。
1. **心情只调制，不生成语义**：它决定选哪个基态、眨眼和扫视频率、头部动作幅度、灯色冷暖，但不会让设备「表示理解」或「表示同意」。会话里 Host 的语义永远覆盖本地心情；心情只影响幅度和节奏（困的时候点头慢一点，不会把点头换成别的）。
2. **基态推导**（可单测的纯函数）：energy < 0.08 → 睡着；< 0.2 → 困倦；valence > 0.5 且 arousal > 0.4 → 开心；valence > 0.3 且 arousal < 0.3 → 满足；20 min 无人互动 → 无聊；新刺激 → 好奇（数秒）；arousal > 0.6 且 valence < 0 → 受惊 / 不爽；其余 → 平静。
3. **昼夜**：HUB 模式没有本地挂钟，用 Hub 响应的 `Date` 头 + 环境光判断夜间；夜间精力衰减加快、灯全灭、头部空闲动作关闭。NVS 只存三个数和最后互动时间，入睡时或每 10 min 写一次，NVS 满时降级为不持久化。

## 8. 头部动作：本地层与服务端命令的仲裁

| 层 | 例子 | 可被谁抢占 | 回执 |
|---|---|---|---|
| L0 安全 | `safety.stop` | 无 | 现有 |
| L1 服务端命令 | 隐式回应手势、`stackchan_head` 显式动作、`body.presence.set` | L0 | 现有，语义不变 |
| L2 本地反射 clip | 被摸蹭头、被拿起缩头、受惊后缩 | L0、L1 | 不上报 |
| L3 注意力跟随 | 转向运动 / 人脸 | L0–L2 | 不上报 |
| L4 空闲活性 | 偶尔张望、伸懒腰 | L0–L3 | 不上报 |

- 现有 `gesture_busy_` 互斥只用于 L1 内部（服务端命令之间仍然先到先得 + `BUSY`）。L2–L4 由 `UpdateLoop` 的关键帧播放器驱动，不建一次性任务，L1 到达即清空。
- 头部空闲活性**刻意稀疏**：清醒时 20–60 s 一次小张望，不做持续呼吸（舵机微动在安静房间里听得见，也耗电），呼吸感交给眼睛。Reachy 官方对话应用的空闲策略里 60% 的时间什么都不做，可作参照。出厂固件 issue #95 已指出空闲动作耗电，`idle_motion` 必须可关。
- 现有 7 个手势迁进 clip 表作为回归基线，行为逐位不变。
- 前置条件：**缺陷 A**（对话结束后电轨不恢复，待机所有动作被 `CAPTURING` 拒绝）必须先修。`capture_gate.h` 的推导核心已合入，下一步是把控制器里所有关闭采集的路径都改为调用它（宠物方案 §4.1）。

## 10. 权限与隐私

### 10.1 待机本地输出（需要拍板）

输出门是会话作用域，会话关闭后 `Allows()` 一律为 false。宠物大部分行为发生在待机，必须先定规则。建议分两类：

| 类别 | 内容 | 规则 |
|---|---|---|
| 设备原生界面 | 屏幕上的脸、眨眼、眼神、心情、状态灯 | 永远允许。它和现在待机时就在眨眼的脸、网络图标是一类东西，不含 Host 生成内容 |
| 本地物理 / 声音反射 | 头部动作、本地音效 | 读 Owner 常驻许可 `policy.allowed` 中的 Motion / AudioCue，再与设备本地 `pet_mode` / `idle_motion` / `sounds` 设置取交集。会话中仍只按会话计划 |

实现：`DeviceOutputGate` 增加只读方法 `AllowsAmbient(output)`，读已绑定策略的 `allowed`，不改会话语义和契约。

### 10.2 摄像头

即使帧不出设备，家里开着的摄像头也是一个新的感知面，按麦克风同等对待：

- Owner 显式开启（P2：SDK `InputSelection` 增加 `camera`，Mobile 增加开关；契约就位之前，相机功能编译期关闭）。
- 采样时屏幕图标 + 固定一颗灯常亮，不受心情、静默时段影响。
- 帧只在内存里做帧差 / 检测，不存储、不上行、不做身份。
- 注意力层只产出「有无人、方位、远近」；会话内若上报 `attention.state`，同样不带坐标和身份。

### 10.3 麦克风

会话内麦克风沿用现有 Owner 输入许可，不变。待机环境耳见 §6.5，单独许可、默认关。

### 10.4 传感器按隐私分两类

| 类别 | 器件 | 规则 |
|---|---|---|
| 环境 / 身体感知（不涉及人的内容） | 头顶触摸、屏幕触摸、IMU、磁力计、接近 / 环境光、舵机读回、电源、RTC、红外接收（只判有无码）、NFC（只认卡片 UID 对应的玩法） | 随宠物模式默认开启；结果只在设备本地使用 |
| 人相关感知（可能涉及人的影像或声音） | 摄像头、待机环境耳 | Owner 逐项显式开启；工作时屏幕图标 + 固定指示灯常亮；原始数据不存储、不上行、不做身份 |

不做的事：Wi-Fi / BLE 被动扫描附近手机、红外解码家电用途、NFC 卡当身份凭证、相机或麦克风数据上行。

**真机上发现并修掉的崩溃：**
- 现象：开机约 12 s abort，回溯是 `I2cDevice::ReadReg` 的 `ESP_ERROR_CHECK` 超时。
- 原因：DTLS 握手让 core 1 忙上百毫秒，低优先级任务若正持有共享 I2C 总线锁就被饿住，排在后面的 PMIC 读 100 ms 超时后中止。宠物新增的持续轮询和写灯让这种情况几乎必现。
- 修复：
  - 传感器任务优先级升到 10，舵机/灯任务升到 9。
  - StackChan 的电量读取、背光写入改成非致命（读失败就沿用上次值）。
  - 宠物自己轮询电量走新接口 `GetPetPower`。
- 遗留风险：编解码器开关（`cores3_audio_codec.cc`）仍用 `ESP_ERROR_CHECK`，原有 LVGL 任务（优先级 1）读触屏也会持锁。没观察到出事，但属同类风险。

### 15.3 今晚真机验证清单（需要人）

1. **看脸**：深色底、发光眼、两根触角，眨眼、张望、呼吸。约 25–60 s 头会轻轻看一眼再回来。
2. **点脸开对话**：进入后触角随你的音量变亮，灯带出现音量条；**说话时头不动**（采音保持）；回答时头可以动。END 结束。
3. **摸头顶**：
   - 额头 / 头顶 / 后脑分别点，看是否对应「眨眼缩一下 / 耳朵一压一弹 / 往后瞄」。**前后方向是否反了**：串口每 30 s 有一行 `PetSensors: touch f/m/b=`，只摸额头时应是 f 有值。
   - 前→后滑是顺毛（眯眼开心），后→前是逆毛。
   - 按住会安心闭眼；双击出信息卡；连拍会生气。
4. **拿起 / 摇晃 / 敲桌子 / 倾斜**：拿起会惊讶、放下会松口气；摇晃出螺旋眼；敲桌会疑问看过来；斜放时眼睛反向保持水平。

6. **掰头**：用手转头，先挤眼抗议再顺从，松手后回正。
7. **充电**：拔掉 USB 竖耳张望，插上出 ⚡ 气泡。
8. **灯的左右顺序**：假设是 0–5 一侧、6–11 另一侧；若音量条或注意方向的灯反了，改 `stackchan_body.cc` 里的 `kPetLedMap`。
9. **服务端动作优先**：本地片段播放中，Host 下发 `head.gesture` 应立即执行并 accepted → started → completed，无 `BUSY`。只做了代码层验证。

    - 不满意可设 `CONFIG_EIDOLON_PET_FACE=n`，回到原脸。

### 15.5 晚间真机反馈后的修正（2026-11-15 夜）

**头部俯仰（参考 Reachy Mini 静止位）**
- 实测：用头内 IMU 读重力、逐级走俯仰舵机（`reports/desk_pet/*-pitchsweep`）。指令 ≤~16° 都停在机械下限，此时屏幕已朝上约 25°；约 51° 顶到上限堵转（约 60° 朝上）。原回位 45° ≈ 屏幕朝上 52°，离上限只差 6°；原点头（+10°）、perk_up 72°、wake_wobble 58–62°、droop 8° 和多数宠物片段其实都会顶到机械限位触发堵转保护。
- 改法：`config.h` 俯仰限位收为 18°–49°（各留 2° 余量），新增 `SERVO_PITCH_REST_DEG=22`（≈ 屏幕朝上 31°；Reachy Mini 是平视上仰 10°，StackChan 机械下限已高于此，取「对着桌前人脸」的同等意图）。手势、自检、宠物片段都改为「静止位 + 偏移」并夹在限位内；`HeadKey.pitch_dd` 改为相对量 `dpitch_dd`。`look_at` 的 y=0 仍对应静止位，上下两半各自映射到对应限位。真机复测静止时 IMU 读数 31.1°，10 分钟内 0 次堵转。
- 顺带：头一动，光线传感器视野跟着变（低头离开台灯会被读成关灯）。头部运动窗口现在同时让光线识别器忽略并重新学习基线。

**界面（11-16 定稿）**
- 状态栏只显示、不可点：左侧只在出问题时显示状态文字；右侧网络、电池，静音时加一个红色麦克风。顶部正中一根把手提示可下拉。
- 操作全部在下拉控制面板里：点状态栏任意位置（整条 320×36 是一个点击区）或从顶部往下拖，面板滑下、背后压暗。按钮 84×76，只显示当前可用的：通话（会话外绿色接通＝JOIN，受 `EIDOLON_PET_SESSION_BUTTON` 控制，调试期默认开；会话内红色挂断，听筒转 135°）、静音（会话中；静音时变红）、设置。点压暗处、5 s 无操作或执行任一按钮后收起。结束会话需两步，防误触。点脸开会话不变。
- 会话状态全部由两根天线的灯头表达（`Runtime::ComposeTips`，主机测试 `TestAntennaeCarrySessionState`）：空闲＝眼色微亮；连接中＝蓝色呼吸；倾听＝薄荷绿随音量发亮；思考（含服务端 Ponder 表情）＝蓝色左右交替闪，不再在脸旁显示「…」；说话＝眼色，随它自己的声音亮暗（11-16 起，见下）；静音＝暗红；出错＝红色闪烁。动作回执也走天线：执行中增亮，完成白闪一下，失败红色闪两下。
- StackChan 不显示字幕。信息卡（头顶双击）两行排列。
- 宠物不调背光（去掉睡眠/暗室调暗），始终是用户设置的亮度。

**帧率（11-16）**
- 实测改前：空闲约 5 帧/秒、每帧 100 ms。原因：StackChan 绘制缓冲只有 10 行单缓冲，一帧约 170 行要分约 17 条，每条都把整张脸的绘制重跑一遍。
- 改法：
  - 脸拆成 9 个部件（左右眼含眉与腮红、左右天线、嘴、表情符号、气泡、粒子、信息卡），每个部件一个绘制函数。同一函数在「记录模式」下不绘制，只把交给 LVGL 的整数参数记入签名、把整数包围盒并成范围（`SkinRec`）；只重画签名变了的部件（新旧位置都刷），每条只画与之相交的部件。签名和范围来自绘制代码本身，不会与屏上内容脱节（之前手写量化签名漏刷过：1/4 像素桶跨过 .5 取整边界、圆心与半径各自不变而相加翻格）。
  - 眼睛两层半透明光晕、天线光晕和杆子改为预混色不透明填充（下面只有纯色背景，外观一致）：光晕原占眼睛渲染时间的 67%。
  - 渲染任务（优先级 1）在 StackChan 上不固定核，只用两核空闲时间。
- 结果：空闲每帧约 22–25 ms（4 倍）；会话中回答阶段约 12–14 帧/秒（改前约 5）；会话中最低剩余内部内存约 38.5 KB，空闲 47 KB。
- 试过无收益已撤回：双缓冲（还多占 6.4 KB，会话中最低内存降到 34 KB）、20 行条带、圆角遮罩缓存 4→16。PSRAM 绘制缓冲不可用（SPI 每次传输要临时申请内部 DMA 缓冲，内存紧时卡死刷新）。
- 渲染测试改为按真实 10 行条带逐帧刷到模拟面板，再与整幅重画逐像素比对：15 个画面及「思考」场景每一帧都完全一致（最大差 0/255）。30 秒统计行常驻 `fps=` 与 `frame_ms`。

**对话中的动效（11-16，从体验出发）**
- 原则：对话时声音优先，渲染只用剩下的 CPU（不提渲染优先级、不加缓冲）；大位移在低帧率下像瞬移，亮暗与小幅变化在低帧率下仍顺，所以对话中屏幕只做小而柔的变化。用户定：倾听、思考、说话时头都不动，只动表情。
- 头：本地反应（被摸等）在倾听 / 思考期间不排头部片段，脸照常反应；服务端 L1 手势不变。打开会话那一下（perk up）不受影响。（说话期间头可以动，见下一节。）
- 说话：天线灯随它自己的声音亮暗（设备已有的播放 RMS `eidolon_livekit_board_recent_playback_rms_ppm`，按该声音近期峰值归一，峰值每秒回落 3 dB，音量设置不影响观感）；天线杆随音节轻轻抬起摆动（天线本来每帧都在重画，几乎不加开销）；眼睛看着你，每 2–5 s 像人说话时那样短暂看一眼旁边（0.7–1.4 s，幅度 ≤0.2）；明显强调处眼睛睁大约 3%，两次至少隔 1.2 s。
- 思考：视线目标从 (.45,-.5) 收到 (.3,-.32)，摆动幅度减小。
- 会话中视线目标缓动（时间常数 0.16 s），轮次切换的弹跳从 1.5 减到 0.45；进入 / 离开会话仍保留「啪」的一下。会话中停掉阶梯呼吸（每一档都整块重画两只眼，在音频忙时是周期性的卡顿）。
- 代价实测（主机渲染测试，按 10 行条带）：说话时每帧重画约 13.5% 屏幕，主机上每帧渲染时间与旧版相同（约 46 µs）；逐音节睁眼的方案是 20.6%，已放弃。新增 30 秒统计行 `stats 30s by phase: listen=帧数@平均帧时 think=… speak=…`，用来在真机对话中看各阶段的流畅度（1000 / 帧时 = 最多能出的帧数）。
- 自动化：`TestHeadStaysStillDuringATurn`、`TestNoBreathingInConversation`、`TestSpeakingFaceFollowsItsVoice`（含小音量设置）、`TestConversationGazeEases`（12 帧/秒下每帧视线位移 < 0.1）；每条都做过反向验证（去掉对应逻辑测试即失败）。渲染测试新增「说话」场景，逐帧与整幅重画比对一致（0/255）。

**音效与说话时的头部动作（11-16 第二轮，用户要求）**
- 用户改定：说话时麦克风是关的（半双工），头可以动；倾听 / 思考时（麦克风开着）头仍不动（`MicOpen`）。
- 说话时的头：重音处小幅点头（上抬约 4° 再回，≥1.2 s 一次），眼睛看旁边时头跟着转 3–6° 再回（先眼后头），都以回到原位结束；服务端 Host 计划在场时本地不动；服务端手势（如回复开头的 perk_up）照旧。说话一结束（约 1.2 s 后开麦）立即 `SettlePetHead` 取消本地片段回原位，免得开麦时头停在半路。说话期间被摸，头也会照常反应。
- 音效：设备合成（`pet_sound.*`，不需要音频文件），每种触摸 / 体感反应一个短音（80–700 ms），由一个工作任务 `pet_chirp_player` 播放，界面不阻塞；连拍时只保留最新一个，不积压。映射：拍前部 bip、拍中间 boing、拍后部 huh、顺毛摸 / 手放着 purr、逆毛摸 / 被扳头 grumble、连拍 hmph、双击 pop、被拿起 eep、放下 phew、摇晃 dizzy、敲桌 knock、遮住 hmm、拿开 peekaboo、关灯 yawn、开灯 wake、脸凑近 giggle、插电 yum、低电量 sad；手靠近、倾斜、摸脸等高频事件不出声。
- 只在会话外出声：倾听 / 思考时麦克风开着，音效会被当成说话；说话时扬声器是它的声音。另需 Owner 常驻许可 `AudioCue`（§10.1，`AllowsAmbient`）；暗室音量减半。日志 `chirp <名字> idle= allowed= played=` 可查每次是否放出。

**触摸方向与音色（11-16 第三轮）**
- 触摸条前后装反了，已改：M5Stack 两份代码对 Si12T 通道顺序说法相反（出厂固件以通道 1 为前，StackChan-BSP 反过来），原实现跟了出厂固件。真机证据：用户拍靠近脸的位置，11 次里 10 次判为「后部」；从前往后摸判成逆毛。现以通道 3 为前（`pet_sensors.cc`），轻拍分区与顺逆毛一起纠正。

- 自动化把「意思」写成可检查的规则（自相关测音高，32 kHz 分析）：疑问类（huh / knock / hmm / wake）句尾比开头高 15% 以上，松口气 / 委屈 / 哈欠 / 哼句尾低 13% 以上，受惊最高 >1.1 kHz，开心均值是委屈的 1.6 倍以上，不满偏低；250 Hz 以下能量 <3%；1 ms 响度不突变（咔哒检测，去掉淡入淡出即 27 处失败）。
- 试听页：每个反应在出声那一刻的屏幕画面（渲染测试导出，逐像素一致）+ 对应声音，https://claude.ai/artifact/9Lhr574vBg3jTVVoTJ79B7 。
- 「100% on power / feeling calm」文字来自双击弹出的信息卡（电量 + 心情）。连拍时第二下落在 0.32 s 内就会被判成双击，容易误触出卡。

**快速轻拍被芯片合并（11-16 第四轮，先错后改）**
- 已拍板：顺毛 / 逆毛方向保持原设计（用户 11-16：问题 1 不改）。
- 第一次判断是错的：把「松开 → 再按下」间隔 40–120 ms 的那些按下当成手指离开时的读数抖动，加了 130 ms 合并。真机复测推翻：单拍从不抖动（有意单拍 0 次），被合并掉的恰恰是用户真实的第二下，双击和连拍因此全部失效。已撤掉，之前那些「误判双击」其实就是用户随手的快速两下。
- 真正的问题：有标注的复测里，三次有意双击各自读成一次 250–300 ms 的按下（单拍约 150 ms），五下快速连拍读成一次 1.15 s 的「按住」（发出满足的 purr，与「拍太多会生气」相反）。Si12T 与 ADSemiconductor TSM12 寄存器兼容（TSM12 规格书 v2.2 §8.2.2–8.2.3）：出厂初始化让芯片开着休眠（CTRL2 0x0F → 0x07，SLEEP=1，规格书说休眠会让响应变长），CTRL1 0x22 是快慢交替扫描、响应 4 个周期。芯片自己就把短暂的抬手吃掉了。
- 修法（`pet_sensors.cc`）：关休眠（CTRL2 0x0B → 0x03），只用快速扫描（CTRL1 0xA2：MS=1，FTC 与 4 周期响应保持出厂值），多耗电约几十微安；触摸改 40 Hz 轮询（tick 25 ms，IMU 仍 20 Hz 读 FIFO，接近 10 Hz、照度 2 Hz 不变）。识别器不再合并任何按下：中间有一个松开采样就是两下。
- 诊断：每次按下结束记一行 `PetSensors: touch press gap=… dur=… peak f/m/b=…`（距上次松开、按了多久、三区最大强度），阈值按它调。
- 自动化：`TestFastTapsStaySeparate`（25 / 50 / 100 ms 间隔都是双击；五下快拍是一次 rapid 而非 hold）、`TestPressSummary`；触摸测试步长改为 25 ms 与设备一致，全部通过。是否真能分开快拍要看真机复测的 `touch press` 行。
- 真机复测（14:04）：单拍 5/5 出 bip；三次双击都识别（两下间隔 76–101 ms，旧芯片设置下会被合成一下、130 ms 过滤也会吞掉），各出 pop；空闲 2 分钟无误触。连拍只在约 3 s 后才出 hmph：拍的过程中有的按了 540–776 ms（超过轻拍上限 300 ms、又不到按住 800 ms，不计数也没有任何反应），而连着两下快的又先被判成双击、弹出信息卡。用户 11-16 定：修。
- 连拍修法：没滑动、不到按住（800 ms）就松开的按下都算一下轻拍（`tap_max_ms` 300 → 800），慢的单拍和连拍里按得久的那几下也有反应、也计数；双击的第二下松开后再等 320 ms，期间没有第三下才报 TouchDoubleTap（信息卡晚约 0.3 s），有第三下就是连拍、不弹卡；第 4 下报 TouchRapid（hmph），同一阵连拍里之后的拍不再报轻拍；运行时在「拍太多」反应期间，新的按下不把脸换回「手放头上」。
- 自动化：`TestDoubleTap`（推迟上报的时刻、第三下取消）、`TestRapidOncePerBurst`（途中无双击、之后不报轻拍）、`TestFastTapsStaySeparate`（按日志里 775/100/100/550 ms 的拍第 4 下即 rapid）、`TestPattingKeepsItAnnoyed`；三处改动分别还原都会让测试失败。
- 真机复测（14:25）：连拍第 4 下 hmph、途中不弹卡、之后的拍不再 bip，按住 purr，都对。双击第一次没出卡：两下间隔 384 ms，超过 320 ms 配对窗口，判成两次单拍；第二次间隔 112 ms 出卡。今天有意双击的间隔 76–384 ms，分开的单拍从不小于 840 ms，于是配对窗口 `double_tap_gap_ms` 改 450 ms，等第三下的时间单独为 `double_tap_wait_ms` = 320 ms（卡不必等更久）。新增「384 ms 也配对」测试。刷入后开机正常。

**会话语音电平（已查清，非本分支问题）**
- 23:05/23:07 两次会话识别失败时怀疑电平偏低。用临时自动入会固件 + Mac `say` 播放固定语句做 A/B（`reports/desk_pet/mic-ab-*`）。
- 第一版测试按固定间隔播放，第二三句落在伙伴回答期间，半双工下麦克风关闭而丢失，造成"只识别一句"的假象（用户指出）。改为轮流说话后：未改动的 main 与本分支三句都全部识别，每句峰值电平都在 0.008–0.010，无差别。
- 结论：本分支未降低麦克风电平。

**堵转保护误判（原有缺陷，本分支放大后已修）**
- 头靠自重静态下垂约 20 个刻度（≈6.5°，IMU 印证），原判定"目标差 ≥8 刻度 + 位置不动 + 负载跳升"在下垂静止时一来新指令就成立，并永久缩小运行时限位。基线 main 开机即把上限学成 23.4°；本分支限位收窄后会把俯仰锁死在 18°。
- 修法（`scs_servo.h`，仅 StackChan）：目标差门槛 24 刻度、确认 4 次；限位已在机械限位以内，只有在限位边缘 4° 内的堵转才学习限位，范围中间的"堵转"只记日志、继续驱动。修后多轮会话与开机 0 次堵转，`perk_up` 正常完成。
- 静止时 `head_level` 判定放宽到 10°（下垂约 7°，原 5° 使倾斜/水平事件总被丢弃）。
- 新增日志 `StackChanBody: settled: readback yaw/pitch`：与 `PetSensors ... g=` 对照，可区分头下垂/被挡住与底座倾斜。11-15 夜读回 25.6°、11-16 读回 30.0°（目标 22°），IMU 39–42°，判断为重新插线后线缆或摆放把头撑住，属物理原因；舵机持续顶着会发热，需理线。
- 调试注意：刷机后立刻拨 RTS 复位再读串口，两次把 S3 的 USB 串口卡死（ROM 后无输出、esptool 连不上），只能重插。改用 esptool `--after hard_reset` 复位、读串口时不拨 RTS 后未再出现。
